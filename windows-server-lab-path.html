Windows Server Lab Path

Build a Windows Server environment on your own hardware or campus lab computers. Use the same virtual machines from setup through file access testing. You’ll need access to a hypervisor and Windows installation media.

Check off the results you observe in your VMs. Progress is saved in this browser when storage is available.

Client brief · NewVue Health

NewVue Health is opening a small billing office. Finance staff currently save test spreadsheets on individual PCs. The IT manager wants a central location, consistent sign-in, and proof that staff outside Finance cannot open the share. You are the junior administrator building a proof of concept before the office opens.

Acceptance criteria

  • Run the pilot on a VM-only network with one domain controller, one member file server, and one Windows workstation.
  • Provide centralized sign-in through Active Directory and internal DNS.
  • Allow a standard Finance user to read and create files. A standard non-Finance user must receive Access Denied using the same share path.
  • Give the IT manager the inventory, group design, permissions, and test results. Use fictional records and omit credentials.
  1. Build the virtual lab
  2. Build the Active Directory domain
  3. Create department users and groups
  4. Configure and verify a departmental share

Lab 1 · Build the virtual lab

Before you start · allow 2–3 hours plus downloads

This walkthrough assumes an x64 Windows host and one installed hypervisor. Use Windows Server 2025 x64 with Desktop Experience and Windows 11 Pro or Enterprise x64. Use school-provided media or obtain Windows Server evaluation media and Windows 11 media from Microsoft. Confirm you can run three guests at once. With the suggested settings below, guests use 12 GB of RAM total, plus the host’s own memory. Dynamic virtual disks start small and expand as data is written.

Use LAB-PRIVATE as the VM-only network name. Keep all guests off the campus or home LAN. If Windows 11 first-run setup for your edition and media requires internet access, temporarily use the hypervisor’s NAT option on SA-CL1 only to finish supported setup. Hyper-V calls its built-in NAT network Default Switch on Windows client hosts, where available. Shut down the client and switch it back to LAB-PRIVATE before applying lab IP settings. For campus computers, use the instructor’s approved Windows deployment process.

Choose one hypervisor and build all three VMs

Hyper-V Manager · Private virtual switch
  1. Open Hyper-V Manager. Select your host in the left pane. In Actions, open Virtual Switch Manager. Select New virtual network switch → Private → Create Virtual Switch. Enter LAB-PRIVATE, select Apply, then OK.
  2. For each inventory row select New → Virtual Machine. Enter the VM name, select Generation 2, and assign 4096 MB startup memory. In Configure Networking choose LAB-PRIVATE. In Connect Virtual Hard Disk choose Create a virtual hard disk, enter the capacity from the inventory, and keep a separate VHDX for each VM.
  3. In Installation Options select Install an operating system from a bootable image file. Browse to the Server ISO for SA-DC1 and SA-FS1, or the Windows 11 ISO for SA-CL1. Finish the wizard.
  4. Before starting each VM, open its Settings → Processor and set 2 virtual processors. Under Security, keep Secure Boot enabled with the Microsoft Windows template. For SA-CL1 also enable Trusted Platform Module.
  5. Right-click the VM and select Connect → Start. Click the console and press a key when prompted to boot from DVD. If the installer is skipped, stop the blank VM and check Settings → Firmware for the mounted DVD and boot order. Continue with the common Windows installation steps below.
VMware Workstation Pro · LAN Segment
  1. Select File → New Virtual Machine → Typical. Choose I will install the operating system later to configure the virtual hardware before Windows Setup.
  2. Choose Microsoft Windows and the matching 64-bit guest profile for the ISO. Enter the VM name and storage location, then set the disk capacity using the inventory. Leave Allocate all disk space now cleared if shown. Finish and leave the VM powered off.
  3. Open VM → Settings → Hardware. Set Memory to 4096 MB. Under Processors use one processor with two cores. Select the virtual CD/DVD drive, choose Use ISO image file, browse to the matching ISO, and select Connect at power on.
  4. In Hardware → Network Adapter select LAN segment. On the first VM select LAN Segments → Add and enter LAB-PRIVATE. Select LAB-PRIVATE from the list and keep Connect at power on selected. For the remaining VMs select the existing segment. Use a single adapter per VM.
  5. For SA-CL1, open Options → Advanced, choose UEFI and enable Secure Boot. In Options → Access Control, encrypt the VM or the files needed for TPM if your version offers that choice. Keep the recovery password. In Hardware → Add select Trusted Platform Module unless the guest profile has already added it.
  6. Power on the VM and click into its console. Boot from the attached ISO and continue with the common Windows installation steps.
Oracle VirtualBox · Internal Network
  1. Select New in VirtualBox Manager. Enter the VM name, select the matching ISO and Windows guest type, and choose Skip Unattended Installation or clear the unattended-install option, depending on your version.
  2. On the hardware screen allocate 4096 MB of RAM and 2 processors. Create a new virtual disk with the capacity from the inventory. Keep full-size preallocation disabled if shown. Finish and leave the VM powered off.
  3. Open Settings → Network → Adapter 1. Select Enable Network Adapter. Set Attached to to Internal Network, enter LAB-PRIVATE as the name, and confirm Cable Connected in Advanced settings. Use the exact same network name for all VMs and leave the other adapters disabled.
  4. Open Settings → System → Motherboard. For SA-CL1 turn on EFI/UEFI and Secure Boot and select TPM 2.0. If the ISO is missing, open Settings → Storage, select the optical drive and choose the matching ISO using the disk icon.
  5. Select Start, click into the VM console, and boot from the ISO. Continue with the common Windows installation steps.

Install Windows inside all three VMs

  1. On each server, begin Windows Server Setup, choose the language and keyboard, and select the install option. Choose Windows Server Standard (Desktop Experience) or its evaluation equivalent. Accept the license. If Setup offers an installation type, choose the custom installation option. Select the new VM’s unallocated disk and continue. Set a unique local Administrator password when prompted.
  2. On SA-CL1, install Windows 11 Pro or Enterprise from the Windows 11 ISO. Select the VM’s empty disk and finish supported first-run setup. Sign in with an account that has local administrator rights. If you used temporary NAT, switch back to LAB-PRIVATE with the guest shut down.
  3. After the first reboot, let the VM boot from its virtual disk. If Setup starts again, remove the ISO from the virtual DVD drive or move the disk above DVD in the boot order.
  4. In each guest press Win+R, run sysdm.cpl, open Computer Name → Change, and set the computer name from the inventory. Leave it in a workgroup and restart. Setting the VM name in the hypervisor does not rename Windows.

Assign the pilot IP addresses

  1. On each guest press Win+R, run ncpa.cpl, right-click the connected Ethernet adapter and select Properties. Select Internet Protocol Version 4 (TCP/IPv4) → Properties.
  2. Select Use the following IP address. Enter that guest’s IPv4 address from the inventory and mask 255.255.255.0. Leave the default gateway blank. The DC’s DNS address remains blank until Lab 2, when you will point all guests at 192.168.77.10. Apply the settings.
  3. Open PowerShell and run hostname and ipconfig /all. Expect the name and address in your inventory, an empty gateway, and one connected lab adapter. If an address starts with 169.254, reopen the adapter properties and check that the static address was saved. If the adapter reports media disconnected, check the hypervisor switch or cable setting.
Verify in your VMs

Evidence and what to keep

Keep the three VMs, the switch, and a record of computer names and addresses.

Next lab · Build the Active Directory domain

Lab 2 · Build the Active Directory domain

Required setup

Complete Lab 1 · Build the virtual lab and use the environment it produces.

Use the three running VMs from Lab 1. Confirm the addresses and switch attachments before starting.

Install AD DS on SA-DC1 · allow 60–90 minutes

  1. Sign in to SA-DC1 as local Administrator. Open Server Manager → Manage → Add Roles and Features. Continue past Before You Begin, select Role-based or feature-based installation, and select SA-DC1 from the server pool.
  2. On Server Roles, select Active Directory Domain Services. In the prompt select Add Features. Continue through Features and AD DS, review the selection, and select Install. Wait for Installation succeeded.
  3. In Server Manager select the notification flag and Promote this server to a domain controller. Select Add a new forest and enter ad.academy.test.
  4. On Domain Controller Options, keep DNS Server and Global Catalog selected and use the wizard’s default functional levels for this single-version lab. Enter and confirm a unique DSRM password and store it privately. On DNS Options, a delegation warning is expected for this isolated new forest. Verify the NetBIOS name AD and keep the default database, log, and SYSVOL paths.
  5. Review your selections, run the prerequisite check, and resolve any blocking errors before selecting Install. After restart sign in as AD\Administrator. In Server Manager open Tools → DNS and confirm the forward lookup zone for ad.academy.test is present.

Point the guests at internal DNS and join the domain

  1. On all three guests open ncpa.cpl and the lab adapter’s IPv4 properties again. Select Use the following DNS server addresses, enter 192.168.77.10 for Preferred DNS server, leave Alternate DNS blank, and apply.
  2. From PowerShell on SA-FS1 and SA-CL1 run Resolve-DnsName -Name _ldap._tcp.dc._msdcs.ad.academy.test -Type SRV. Expect SA-DC1 to appear as the target. If it fails, confirm the DNS address, virtual network membership, and DNS service before joining the domain.
  3. On SA-FS1 open sysdm.cpl, then Computer Name → Change. Under Member of select Domain and enter ad.academy.test. Enter authorized credentials such as AD\Administrator when prompted. Expect a Welcome to the domain message. Restart and repeat on SA-CL1.
  4. On both member machines run (Get-CimInstance Win32_ComputerSystem).Domain and record the results. From SA-CL1 run Resolve-DnsName SA-FS1.ad.academy.test. Expect 192.168.77.20. If the member record is missing, confirm SA-FS1 uses internal DNS, run ipconfig /registerdns there as administrator, then retry.
Verify in your VMs

Evidence and what to keep

Keep the domain controller, DNS settings, and both domain members. Record successful lookup and join results.

Next lab · Create department users and groups

Lab 3 · Create department users and groups

Required setup

Complete Lab 2 · Build the Active Directory domain and use the environment it produces.

Use the working domain and joined client from Lab 2. Confirm SA-CL1 can discover the domain controller.

Create the Finance access model · allow 30–45 minutes

  1. On SA-DC1, open Server Manager → Tools → Active Directory Users and Computers. Expand ad.academy.test. Right-click the domain and select New → Organizational Unit. Name it Departments. Repeat inside Departments to create Finance.
  2. Right-click Finance and select New → Group. Enter GG-Finance, choose Global scope and Security type. Create DL-Finance-Modify in the same OU using Domain local scope and Security type.
  3. In Finance, select New → User. Use the name Finance Test and user logon name finance.test. Under Departments, create a second user named Outside Finance Test with logon name outsider.test. Set separate temporary passwords and keep the option to change them at first logon. Enable both accounts and leave them as standard users.
  4. Open GG-Finance → Properties → Members → Add. Enter finance.test, select Check Names, and confirm. Open DL-Finance-Modify → Properties → Members → Add and add GG-Finance. The global group represents the department. The domain-local group represents permission on the resource.
  5. In the SA-CL1 VM console, select Other user and sign in as AD\finance.test. Change the temporary password if prompted. Run whoami and whoami /groups. Expect the Finance identity and GG-Finance membership.
  6. Sign out completely and repeat for AD\outsider.test. Expect a successful domain sign-in and no GG-Finance membership. If a recent change is missing, sign out and back in so Windows builds a fresh sign-in token.
Verify in your VMs

Evidence and what to keep

Keep the test accounts, group memberships, and joined workstation for the access tests.

Next lab · Configure and verify a departmental share

Lab 4 · Configure and verify a departmental share

Required setup

Complete Lab 3 · Create department users and groups and use the environment it produces.

Use the same domain, joined file server and client, and two test identities from Labs 1–3. Confirm SA-CL1 resolves SA-FS1 by name and both test accounts can sign in.

Set folder permissions on SA-FS1 · allow 45–60 minutes

  1. Sign in to SA-FS1 as an administrator. In File Explorer open C:\. Use New → Folder to create LabShares, then create Finance inside it. Limit the following changes to the new Finance folder.
  2. Right-click Finance and choose Properties → Security → Advanced. Select Disable inheritance → Convert inherited permissions into explicit permissions. Keep SYSTEM and the local Administrators group with Full Control. Remove broad entries such as Users or Authenticated Users, if present, from this lab folder. Confirm the administrator entries remain before applying.
  3. Select Add → Select a principal. Enter AD\DL-Finance-Modify, select Check Names, and confirm. Set Type to Allow, Applies to to This folder, subfolders and files, and select Modify. Apply and reopen Advanced Security to verify. As administrator, create a fictional budget-sample.txt in Finance.

Publish the share and test from the client

  1. Open Finance Properties → Sharing → Advanced Sharing. Select Share this folder and set Share name to Finance. Open Permissions. Add AD\DL-Finance-Modify and allow Change and Read. Add the file server’s local Administrators group with Full Control and remove Everyone if present. Apply the changes.
  2. On SA-CL1 run Test-NetConnection SA-FS1.ad.academy.test -Port 445. If DNS resolves but the TCP test fails, on SA-FS1 open wf.msc, select Inbound Rules, and check File and Printer Sharing (SMB-In) is enabled for the Domain profile. Then retest.
  3. On SA-CL1 sign in as AD\finance.test. Enter \\SA-FS1.ad.academy.test\Finance in File Explorer. Open budget-sample.txt, create finance-proof.txt, and record the result with the signed-in identity. Then sign out completely.
  4. Sign in as AD\outsider.test and enter the exact same UNC path. Record Access Denied. If Windows prompts for alternate credentials, cancel and record that the account could not open the share. Do not enter Finance credentials. If both users get denied, inspect the group nesting and both permission layers. If both get in, look for a broad permission in the share or NTFS ACL.
  5. On SA-FS1 run Get-SmbShareAccess -Name Finance and (Get-Acl 'C:\LabShares\Finance').Access. Record both outputs and confirm they match the assignment. SMB network access is governed by both sets of permissions.
Verify in your VMs

Evidence and what to keep

Submit the share and NTFS permissions, both client test results, and a short configuration handoff. Keep the domain for future Academy labs.
